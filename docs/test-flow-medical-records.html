FASE 2 Eksekusi SQL — buat tabel omnicare_medical_record ▾

Action

SQL pakai CREATE TABLE IF NOT EXISTS — aman dijalankan berulang tanpa risiko data loss.

Backup dulu walau idempotent — best practice: 
mysqldump -u DB_USER -p DB_NAME > backup-before-medical-$(date +%Y%m%d).sql

Eksekusi SQL via phpMyAdmin (hPanel → Databases → phpMyAdmin → pilih DB → SQL tab → paste isi file) atau via SSH:

mysql -u DB_USER -p DB_NAME < {PROJECT_PATH}/database/sql/2026_06_02_omnicare_medical_records.sql

Verifikasi

Query phpMyAdmin atau mysql:

SHOW TABLES LIKE 'omnicare_medical_record';
DESCRIBE omnicare_medical_record;
SELECT COUNT(*) FROM omnicare_medical_record;

Expected: tabel ada, ~50 kolom, count = 0 (kosong, belum di-populate).

FASE 3 Test sync kecil — 1 cabang 1 bulan (smoke test) ▾

Sebelum backfill 5 tahun, validasi dulu lewat sync 1 cabang 1 bulan Bintaro Mei 2026 (~350 records).

Action

cd {PROJECT_PATH} && {PHP_PATH} artisan omnicare:sync --endpoint=medical --place=29957 --start=20260501 --end=20260531

Expected output:

◉ Branch 29957
  /get/all_medical_records (20260501-20260531)
    ✓ ~350 medical records (across ~4 pages)
Sync complete

Verifikasi

SELECT COUNT(*) total,
       SUM(CASE WHEN chief_complaint IS NOT NULL THEN 1 ELSE 0 END) ada_complaint,
       SUM(CASE WHEN diagnose_note IS NOT NULL THEN 1 ELSE 0 END) ada_diagnose,
       SUM(CASE WHEN procedures IS NOT NULL THEN 1 ELSE 0 END) ada_procedures
FROM omnicare_medical_record
WHERE branch_id='29957' AND date BETWEEN '2026-05-01' AND '2026-05-31';

Expected: total ~340-360 (angka eksak bisa beda kalau Omnicare ada koreksi data), mayoritas ada_procedures > 0.

Trouble: total = 0 atau "✗" error

Cek log: tail -50 storage/logs/omnicare-*.log

Kalau code 598 "Invalid JSON" → koneksi internet bermasalah, retry.

Kalau code 599 → timeout, naikkan OMNICARE_TIMEOUT di .env.

Kalau code lain → hubungi Ekky.

FASE 5 Sign-off — verifikasi cron daily + spot check rekam medis ▾

Verifikasi cron tetap bekerja

TIDAK ADA cron baru dibuat. Default command omnicare:sync yang sudah jalan di 02:00 sekarang otomatis include endpoint medical.

Verifikasi besok pagi setelah cron 02:00 jalan:

SELECT MAX(date), MAX(last_synced_at)
FROM omnicare_medical_record;

Expected: last_synced_at = hari sekarang (bukti cron menyentuh tabel ini).

Spot check — bandingkan sample dengan Omnicare

Pilih 3 rekam medis acak, banding dengan Omnicare langsung:

SELECT record_id, date, p_name, doctor, booking_code,
       LEFT(chief_complaint, 80) chief,
       LEFT(diagnose_note, 80) diag,
       LEFT(procedures, 80) procs
FROM omnicare_medical_record
WHERE chief_complaint IS NOT NULL
ORDER BY RAND()
LIMIT 3;

Buka Omnicare → cari pasien dengan booking_code sample → banding isi rekam medis. Harus 100% match.

Coverage check

SELECT
  COUNT(*) total,
  SUM(CASE WHEN chief_complaint IS NOT NULL THEN 1 ELSE 0 END) ada_keluhan,
  SUM(CASE WHEN diagnose_note IS NOT NULL THEN 1 ELSE 0 END) ada_diagnosa,
  SUM(CASE WHEN treatment_plan_note IS NOT NULL THEN 1 ELSE 0 END) ada_rencana,
  SUM(CASE WHEN procedures IS NOT NULL THEN 1 ELSE 0 END) ada_prosedur,
  SUM(CASE WHEN prescription IS NOT NULL AND TRIM(REPLACE(prescription,';','')) <> '' THEN 1 ELSE 0 END) ada_resep
FROM omnicare_medical_record;

Catat % isian per field — coverage rendah di field tertentu (misal chief_complaint) biasanya karena dokter tidak isi konsisten, BUKAN bug sync.
